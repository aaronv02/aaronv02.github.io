03 — PRIVACY & SECURITY

Your most valuable ideas should not become someone else's API request.

Claim Forge runs every model on your hardware and keeps every project in an encrypted local vault. There is no account, no server component, and no telemetry. This page states exactly what that means — and, just as plainly, where the protection stops.

One boundary. Everything you draft stays inside it.

02 — LOCAL VS. CLOUD

What changes when there is no server.

A fair comparison. Cloud AI is not careless with your data — it is simply no longer yours to control once it leaves the machine. The difference is architectural, not attitudinal.

03 — RUNTIME FACTS

Ten facts, enforced by the codebase.

These are not policies or intentions. Each is a property of the software as it exists today, verifiable in the repository.

RUNTIME FACTS — FROM THE CODEBASE
  1. 01

    Runs fully offline

    Claim Forge makes zero network calls at runtime. You can draft with Wi-Fi disabled; nothing changes.

  2. 02

    No telemetry

    No analytics, no crash reporters, no usage pings. There is no server-side component to collect anything.

  3. 03

    Local inference only

    All models run via Ollama on 127.0.0.1—your text is processed by weights on your own disk, never by an API.

  4. 04

    Per-project encrypted vault

    Each project lives in an encrypted vault at ~/.claimforge: PBKDF2-HMAC-SHA256 with 480,000 iterations derives the key, Fernet (AES) encrypts the contents.

  5. 05

    Key held in memory only

    The vault key is derived from your passphrase and kept in memory while you work. It is never written to disk.

  6. 06

    Append-only audit log

    Every meaningful action in a project is recorded in an append-only audit log, so the drafting history of an invention is traceable.

  7. 07

    Cryptographic erase on delete

    Deleting a project destroys its key material, rendering the encrypted contents unrecoverable—erase by cryptography, not by file deletion.

  8. 08

    Signed offline updates

    Updates are Ed25519-signed packages applied from a local file. The signature is verified offline before anything is installed.

  9. 09

    Loopback-only interface

    The built-in web UI binds to 127.0.0.1 only. It is not reachable from your LAN or the internet.

  10. 10

    Export is an explicit act

    Nothing leaves the vault unless you export it. Exported PDFs are flattened for review; working DOCX files stay inside the vault.

04 — ON YOUR DISK

Everything has a place. All of it is yours.

One vault root, one encrypted store per project subsystem, and three verbs for the vault's whole lifetime: back up, delete, export.

Vault root — default ~/.claimforge

$ tree ~/.claimforge~/.claimforge/├── evidence/<project>/      # originals you import — drawings, photos, audio├── drafts/<project>/        # drafts and claims, encrypted at rest├── exports/<project>/       # packages you build — still inside the vault├── audit/<project>/          # append-only log of actions, never invention content└── sessions/<project>.db    # interview sessions    # memory/, turns/, and approvals/ follow the same per-project scheme

Backup

An encrypted archive you copy yourself. Backups are checksummed snapshots written to a folder you choose; the contents stay encrypted, and a restore still needs the same passphrase.

Delete

A cryptographic erase. Deleting a project destroys its key material, so a recovered file yields only ciphertext — the guarantee rests on the encryption, not on scrubbing bytes. No tombstone is written.

Export

Always explicit. Only the flattened PDF you previewed can leave, written to one folder you name. Nothing is emailed, uploaded, or shared.

05 — TELEMETRY

There is none.

Not off by default — absent. There is no server-side component to collect anything, and the commitment is enforced by the test suite, not just stated in a policy.

No analytics SDK

None is a dependency, and none may be added. There are no usage counters, event pings, or funnels anywhere in the code.

No crash reporting

Crashes stay on your machine. There is no reporter, no upload endpoint, and no diagnostics channel of any kind.

No update polling

Updates are Ed25519-signed packages you fetch yourself and apply from a local file. The app never phones home to check.

Proven by a test

test_no_telemetry.py audits the source and its declared dependencies, and fails the build if a network primitive appears outside the one sanctioned local-model adapter.

Outside our control — your desktop OS and Ollama run their own code under their own policies; what they collect is their configuration, not ours. The threat model assumes a host you trust, and extremely sensitive work belongs on the dedicated offline deployment.

06 — WHAT WE DON'T CLAIM

What we don't claim.

Four limits in the current build. Publishing them is part of the security model — a limitation you hide becomes a promise you cannot keep.

Limit 01

Passphrase strength is your call

Vault security depends on the passphrase you choose. There is no strength meter yet—use a long, unique passphrase.

Mitigation — roadmap

Choose a long, unique passphrase — the 480,000-iteration key derivation only slows guessing, it cannot fix a weak one. Strength guidance at vault creation is planned.

Limit 02

Loopback UI has no authentication

While a vault is unlocked, any process running as your user could call the local interface on 127.0.0.1. Lock the vault when you step away.

Mitigation — roadmap

Run Claim Forge on a machine you trust, and lock the vault when you step away. Request origin checks on the local interface are planned.

Limit 03

App bundle is not yet code-signed

Pre-release builds are not notarized or code-signed, so your OS may warn on first launch. Signing is planned before general availability.

Mitigation — roadmap

Verify the published checksum of any pre-release build before installing it. Signing and notarization are planned before general availability.

Limit 04

No independent penetration test yet

The security design is documented and test-covered, but an independent third-party audit has not been completed.

Mitigation — roadmap

The engagement scope is already written (docs/pen-test-scope.md), and the adversarial self-audit runs in CI in the meantime — but a self-audit is not an independent one.

Assumptions the model rests on

  • Single-user trust. While a vault is unlocked, any process running as your OS user can reach the local interface. Use a machine you control.
  • Host OS integrity. Malware or administrator-level compromise of the host — memory scraping, keylogging — is explicitly out of scope.
  • Physical access. An attacker with your running, unlocked machine is out of scope. The powered-off device is the case the vault defends.
